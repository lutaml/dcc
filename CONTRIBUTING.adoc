= Contributing to the dcc gem

Thank you for your interest in improving the `dcc` gem! This document
covers setup, code style, and the contribution workflow.

== Setup

    $ git clone https://github.com/lutaml/dcc.git
    $ cd dcc
    $ bundle install

Run the test suite:

    $ bundle exec rake

(That runs `bundle exec rspec` then `bundle exec rubocop`.)

== Branch policy

* All changes go through PRs. Never commit to `main`.
* Branch naming: `feat/<short-description>`,
  `fix/<short-description>`, `docs/<short-description>`.
* Squash-merge or rebase-merge into `main`.

== Code quality rules

The project enforces strict rules inherited from Ribose's
https://github.com/riboseinc/oss-guides[OSS guides] plus project-specific
constraints:

=== Forbidden
* `require_relative` inside `lib/` — use Ruby `autoload` instead.
* `require "dcc/..."` with internal paths — autoload only.
* `send` to call private methods — redesign the API boundary.
* `instance_variable_set` / `instance_variable_get` — use accessors.
* `respond_to?` for type checking — use `is_a?` or model the type hierarchy.
* Nokogiri anywhere outside `lib/dcc/validate/xsd.rb` and
  `lib/dcc/migrate/v2_to_v3.rb`.
+
The migration exception exists because a version transform rewrites element
names and moves subtrees on documents the object model cannot round-trip —
doing it through the model would discard the very constructs the transform
has to carry. Revisit and remove this exception when the parser round-trips
a DCC without loss, at which point the transform can run on the model.
* Doubles in specs — use real model instances.
* Hand-rolled `to_h`/`from_h` on model classes — use lutaml-model mappings.

=== Required
* `# frozen_string_literal: true` at the top of every Ruby file.
* `module_eval`/`class_eval` blocks should reference fully-qualified
  constants (e.g. `::Dcc::Namespace::Dcc`).
* Output models (`Dcc::Validate::Result`, `Dcc::Convert::Result`,
  `Dcc::Inspect::Report`, `Dcc::Diff::Result`) must respond to
  `to_s`, `to_json`, and `to_yaml`.
* Public API surfaces should carry YARD `# @param` / `# @return`
  annotations.

== Testing

* Every public method has specs.
* Round-trip specs run over every PTB reference fixture under
  `spec/fixtures/`.
* Schematron rules each have at least one negative spec.

== Commit messages

* Imperative mood: "Add X", "Fix Y", "Document Z".
* First line ≤ 72 characters.
* Body wraps at 72 columns.
* No `Co-authored-by:` trailers for AI tools (per project policy).
* No "Generated with Claude" or similar AI-acknowledgment footers.

== Ribose Contributor License Agreement

Before your first pull request can be merged in any Ribose GitHub
organization, you need to be covered by the Ribose Contributor License
Agreement (CLA). Sign once; one signature covers every Ribose
organization.

* *Individual contributors*: sign the Individual CLA at
  https://cla.ribose.com/icla[cla.ribose.com/icla]. The `cla/ribose`
  check on your pull request reports the state, and you can also sign
  from the pull request by commenting `@ribose-cla agree` and completing
  the one-click link the App replies with.
* *Corporate contributors*: if your employer has an executed
  Organization CLA, the employer's Point of Contact adds your GitHub
  handle to its Schedule A at
  https://cla.ribose.com/organizations[cla.ribose.com/organizations], or
  you can request coverage there yourself. No individual signature is
  then needed.
* *The full guide*: the signing flows and the agreement text are at
  https://github.com/riboseinc/cla/blob/main/docs/SIGNING.md[the Ribose
  CLA signing guide].
